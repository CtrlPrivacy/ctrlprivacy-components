# Writing JavaDocs

Every method in this codebase gets a JavaDoc comment, in `core/` and `web/` alike — public, package-private,
protected, and private methods, including getters/setters not generated by Lombok, constructors with
non-trivial parameters, and interface method declarations. Lombok-generated methods (from `@Data`,
`@Value`, `@Builder`, `@Getter`, etc) don't need hand-written JavaDocs since there's no method body to
document.

#### What to write

Describe what the method does and why, not a restatement of its name. Document `@param` for every
parameter, `@return` for non-void methods, and `@throws` for any checked or unchecked exception the
method deliberately throws (e.g. `CtrlPrivacyException` with a specific `Error`). If a method's
behavior depends on a non-obvious invariant or side effect (e.g. it mutates the database, has a
required call order, or only works given upstream validation), say so.

#### Where it goes

On overridden methods (`@Override`), document the class-specific behavior even if the interface or
superclass already has a JavaDoc — restate anything a reader would need to know about this particular
implementation (e.g. which `Error` this implementation throws, what a particular provider's identity
lookup does differently). Don't just point to the parent JavaDoc.

#### Style

Keep it to the point — a one-line summary is enough for a simple method; add `@param`/`@return`/`@throws`
tags below it when the method has parameters, a return value, or thrown exceptions. Don't restate the
type system (e.g. don't write "the id" for `@param id`; say what the id identifies and where it comes
from if that's not obvious from the name alone).
